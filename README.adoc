= Post-Quantum SSH on Red Hat Enterprise Linux 10

An introductory, hands-on ZeroTouch lab (`zt-security-pqc-ssh`) that walks a participant
through post-quantum cryptography (PQC) for SSH on Red Hat Enterprise Linux 10. No
cryptography background required.

== Audience and objectives

Sysadmins, developers, and security-curious learners new to PQC. By the end, participants can
explain the quantum threat and "harvest now, decrypt later," confirm PQC is enabled in the
`DEFAULT` crypto-policy and OpenSSH, establish an SSH connection that uses the ML-KEM key
exchange, and harden an SSH server to *require* post-quantum key exchange.

== Modules

[cols="1,3,2",options="header"]
|===
| # | Module | What the participant does

| 01 | About This Lab | Reads the quantum threat, PQC, and the lab environment
| 02 | Your Post-Quantum Foundation | Inspects crypto-policy (`DEFAULT`) and `ssh -Q kex` (ML-KEM available)
| 03 | A Post-Quantum SSH Connection | `ssh node1`; proves `mlkem768x25519-sha256` was negotiated with `ssh -v`
| 04 | Require Post-Quantum SSH | Adds an sshd drop-in on node1 requiring ML-KEM; verifies classic clients are refused
|===

Each module ships a `solve-rhel.sh` (all participant commands) and a `validation-rhel.sh`
(pass/fail with actionable hints) under `runtime-automation/module-NN/`. All runtime scripts
run on `rhel` and reach `node1` over SSH.

== Lab environment

Two RHEL 10.1 VMs, both in the `bastions` group:

* *rhel* — the bastion the participant uses (the terminal is logged in here as `rhel`).
* *node1* — the SSH server the participant connects to.

Users `rhel` and `root` exist on both; `rhel` has passwordless sudo.

Image: `rhel-10-1-04-15-26` (see note below). Because PQC is in the `DEFAULT` crypto-policy
on RHEL 10.1+, the lab needs *no* package installs and *no* policy changes — PQC is observed,
used, then enforced.

=== Self-contained inter-VM SSH

`rhel → node1` SSH is wired up by the setup scripts with a *throwaway, lab-only* ed25519
keypair: `setup-automation/setup-rhel.sh` installs the private key and an `~/.ssh/config` for
`node1` (for both `rhel` and `root`); `setup-automation/setup-node1.sh` installs the matching
public key into `authorized_keys`. The key is lab-scoped and disposable.

[IMPORTANT]
====
*Verify these on first deploy — they are the parts this framework does not guarantee:*

. *Image / version.* The supplied image `rhel-10-1-04-15-26` is a RHEL *10.1* image. The PQC
  behavior is identical on 10.1 and 10.2 (PQC is in `DEFAULT` from 10.1 onward). If you truly
  need a 10.2 image, substitute its identifier in `config/instances.yaml` — the content says
  "RHEL 10.1+" and remains correct.
. *Per-VM setup.* This assumes the platform runs `setup-<host>.sh` on each `bastions` VM
  (`setup-rhel.sh` on rhel, `setup-node1.sh` on node1). If node1's setup does not run, the
  lab key is not installed there and `ssh node1` will fail.
. *node1 resolution.* `rhel` must resolve the name `node1`. If the platform provides no DNS
  between the VMs, set `NODE1_IP` (wired through `setup-automation/main.yml`) so setup pins it
  in `/etc/hosts`.
====
