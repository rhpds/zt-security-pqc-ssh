= A Post-Quantum SSH Connection

Time to use it. In this module you will connect from *rhel* to *node1* over SSH and prove
that the connection negotiated the post-quantum *ML-KEM* key exchange — automatically, with
no special flags.

== Step 1 — Connect to node1

From the `rhel` terminal, SSH to `node1`:

[source,bash,role=execute]
----
ssh node1
----

The first time, SSH may ask you to accept node1's host key — type `yes` if prompted. You are
now logged in to *node1* as the `rhel` user. Confirm where you are:

[source,bash,role=execute]
----
hostname
----

It should print `node1`. Return to the `rhel` bastion:

[source,bash,role=execute]
----
exit
----

== Step 2 — Reveal the negotiated key exchange

SSH does not announce the key exchange it chose unless you ask for verbose output. Run a
single remote command with verbose logging and filter for the KEX line:

[source,bash,role=execute]
----
ssh -v node1 true 2>&1 | grep "kex: algorithm:"
----

You should see a line like:

[source,text]
----
debug1: kex: algorithm: mlkem768x25519-sha256
----

[IMPORTANT]
====
That one line is the whole point of the lab: your everyday `ssh node1` just negotiated a
*post-quantum* key exchange. An attacker recording this session cannot decrypt it later with
a quantum computer, because the session key was protected by ML-KEM-768. You did not have to
ask for it — on RHEL 10.1+ it is the default.
====

== Step 3 — Contrast with a classical-only connection

To appreciate the difference, force SSH to use *only* a classical key exchange for one
connection and look at the negotiated algorithm:

[source,bash,role=execute]
----
ssh -o KexAlgorithms=curve25519-sha256 -v node1 true 2>&1 | grep "kex: algorithm:"
----

This time the negotiated algorithm is `curve25519-sha256` — a strong *classical* exchange,
but one with no quantum protection. A recorded session using it would be vulnerable to
"harvest now, decrypt later."

[NOTE]
====
Right now `node1` still accepts *both* post-quantum and classical key exchanges, which is why
the command above succeeds. That is fine for compatibility during a migration — but for truly
sensitive systems you may want to *require* post-quantum key exchange and refuse the
classical fallback. That is exactly what you will do in the final module.
====

Continue to the last module to make post-quantum key exchange mandatory on `node1`.
