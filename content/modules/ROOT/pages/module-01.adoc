## Step 1: About This Lab

== Objective

By the end of this guided lab exercise, you will be able to:

* Explain the quantum threat to cryptography and "harvest now, decrypt later."
* Identify the post-quantum algorithms standardized by NIST (ML-KEM, ML-DSA, SLH-DSA).
* Confirm that post-quantum cryptography is already enabled on Red Hat Enterprise Linux 10.
* Establish an SSH connection that uses a post-quantum key exchange (ML-KEM).
* Harden an SSH server so that it *requires* post-quantum key exchange.

== Introduction

Learn how to protect SSH traffic against future quantum computers using Red Hat Enterprise
Linux 10.

Almost every secure connection you use today — HTTPS, VPNs, and SSH — relies on public-key
cryptography such as RSA and elliptic curve. A sufficiently powerful *quantum computer*
could break those algorithms. The threat is not only in the future: in a *"harvest now,
decrypt later"* attack, an adversary records your encrypted traffic today and simply waits
for a quantum computer to decrypt it later. Any secret that must stay confidential for years
is already at risk.

To address this, in 2024 NIST standardized a new family of *post-quantum* algorithms built
on math problems that neither classical nor quantum computers are known to solve
efficiently: *ML-KEM* (FIPS 203, key exchange), *ML-DSA* (FIPS 204, signatures), and
*SLH-DSA* (FIPS 205, signatures).

Red Hat Enterprise Linux 10 is built to be *post-quantum capable*: these algorithms ship in
its core cryptographic libraries and in OpenSSH. In this lab you will use that capability to
make SSH — the workhorse protocol every administrator relies on — resistant to the quantum
threat.

[NOTE]
====
This lab runs on *RHEL 10.1 or later*, where post-quantum key exchange is part of the
`DEFAULT` system-wide crypto-policy. That means PQC is *already on* — there are no preview
packages to install and no special policy to enable. You will verify it, use it, and then
enforce it.
====
