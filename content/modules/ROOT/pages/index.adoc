= Getting Started with Post-Quantum Cryptography in RHEL 10 OpenSSH

Quantum computers are coming, and they will break the public-key cryptography that protects most of today's network traffic. You do not have to wait for that day to defend against it. Red Hat Enterprise Linux 10 ships post-quantum cryptography (PQC) support directly in OpenSSH, so you can harden your SSH connections right now using the tools and workflows you already know.

In this hands-on lab you play the role of a system administrator securing SSH on RHEL 10. You start by confirming post-quantum key exchange is already built into the system, prove it on a real SSH connection, and finish by hardening the server so a quantum-vulnerable connection is no longer even possible. Everything happens from the command line in about 30 minutes.

== The Threat: Harvest Now, Decrypt Later

Today's SSH connections rely on algorithms like Curve25519 and ECDH to agree on a session key. These are secure against classical computers. They are *not* secure against a large-scale quantum computer.

That gap has a name: *Harvest Now, Decrypt Later* (HNDL).

An attacker who can capture your encrypted traffic does not need to break it today. They record it, store it, and wait. Once a capable quantum computer exists, they decrypt everything they saved. Any data with a long confidentiality lifetime — financial records, health data, state secrets — is at risk the moment it crosses the wire, even if that quantum computer is still years away.

The good news: the fix is already in RHEL 10, and this lab shows you how to use it.

== What You'll Do

This lab is part 1 of a 3-part session, delivered as four short modules:

* *Module 1: About This Lab* — The quantum threat, post-quantum cryptography, and the lab environment.
* *Module 2: Your Post-Quantum Foundation* — Confirm that RHEL 10's `DEFAULT` crypto policy and OpenSSH already support a hybrid ML-KEM key exchange, with nothing extra to install or enable.
* *Module 3: A Post-Quantum SSH Connection* — Connect from `rhel` to `node1` with verbose SSH output and prove the connection negotiated `mlkem768x25519-sha256`, then contrast it with a classical-only connection.
* *Module 4: Require Post-Quantum SSH* — Harden `node1`'s `sshd` configuration so it only accepts a post-quantum key exchange, and confirm a classical-only client is rejected.

By the end, you will be able to:

* Explain the quantum threat to cryptography and "harvest now, decrypt later."
* Confirm that post-quantum cryptography is already enabled on Red Hat Enterprise Linux 10.
* Observe the difference between classical and post-quantum key exchange by inspecting raw SSH handshake logs (`ssh -v`/`-vv`).
* Harden an SSH server so that it *requires* post-quantum key exchange.

== Who This Lab Is For

This lab is written for junior system administrators and anyone new to Linux. It is a beginner-level lab.

You should be comfortable with a few basics before you start:

* Running basic commands in a Linux terminal (`cd`, `ls`, `cat`, and editing a file).
* Connecting to a host over SSH.

No prior cryptography or post-quantum knowledge is required. Every new concept — HNDL, crypto policies, and key exchange — is explained as you go.

== Your Lab Environment

You have your own environment with two Red Hat Enterprise Linux 10 virtual machines:

* *rhel* — the bastion. You run every command in this lab from here.
* *node1* — the host you reach over SSH in modules 3 and 4.

You interact with the environment through a single terminal tab at the side of this screen:

* *>_ terminal* — a shell on the `rhel` bastion. When a step has you connect to `node1`, you run `ssh node1` from this same terminal, then `exit` to return to `rhel` when the module tells you to.

The SSH user on both machines is `rhel`.

Commands shown in a shaded box are ready to run. In this zero-touch environment you can click the command to send it straight to the active terminal — no copy and paste needed.

When you are ready, open *Module 1* to get started.
