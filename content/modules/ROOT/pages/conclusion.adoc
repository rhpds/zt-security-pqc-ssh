= Conclusion and Next Steps

Congratulations — you have confirmed, proven, and then enforced a quantum-resistant SSH connection on Red Hat Enterprise Linux 10, using only the standard command-line tools you already work with every day.

You started with the threat that makes this work urgent: *Harvest Now, Decrypt Later* (HNDL). An attacker does not need to break your encryption today. They can capture your traffic now, store it, and decrypt it later once a capable quantum computer exists. Over four short modules you moved from confirming RHEL 10's post-quantum foundation to a server that refuses to fall back to a quantum-vulnerable connection.

== What You've Learned

Across the four modules of this lab, you learned how to:

* *Confirm your post-quantum foundation.* You read the system-wide `DEFAULT` crypto policy and OpenSSH's supported key exchange algorithms, and confirmed `mlkem768x25519-sha256` — a hybrid post-quantum algorithm — is already available and preferred, with nothing to install or enable.
* *Prove a real connection is post-quantum.* Using `ssh -v`, you read the `debug1: kex: algorithm:` line to see exactly which key exchange a live `rhel` → `node1` connection negotiated, and confirmed it was the hybrid ML-KEM algorithm, not a classical one.
* *Contrast classical and post-quantum handshakes.* You forced a connection to use only a classical key exchange (`curve25519-sha256`) and compared it against the post-quantum default, so you can prove — not just assume — which algorithm is in use on any connection.
* *Require post-quantum key exchange.* You hardened `node1`'s `sshd` configuration to accept only `mlkem768x25519-sha256`, then verified a post-quantum connection still succeeds while a classical-only connection is rejected outright.

== The End-to-End Post-Quantum Story

Each module built on the one before it. Put the pieces together and you can see the full arc:

. *The threat (HNDL).* Classical key exchange algorithms like Curve25519 are safe against today's computers but not against a large-scale quantum one. Traffic captured now can be decrypted later.
. *The foundation (Module 2).* You confirmed RHEL 10's `DEFAULT` crypto policy already includes a hybrid ML-KEM key exchange for OpenSSH — the building block everything else relies on.
. *The proof (Module 3).* You opened a real `rhel` → `node1` SSH session and read the verbose handshake output to confirm ML-KEM was actually negotiated, then saw what a classical-only connection looks like by contrast.
. *The enforcement (Module 4).* You configured `node1` to *require* post-quantum key exchange, closing the door on quantum-vulnerable fallbacks for good.

With the key exchange proven and then required, your SSH connection to `node1` is quantum-resistant by policy, not just by default — and you got there using only `update-crypto-policies`, `ssh -v`, and standard `sshd` configuration. That is the real lesson: adopting post-quantum cryptography on RHEL 10 does not require new workflows. It requires the awareness to confirm post-quantum algorithms are in use and the discipline to require them where it matters.

== Where to Go From Here

This lab is part 1 of a 3-part Red Hat Summit session on post-quantum security. You have the SSH building blocks; here is how to take them further.

* *Apply this hardening at scale.* In this lab you required post-quantum key exchange on one host. In a real estate you would roll the same `sshd` drop-in out to every system — for example with a RHEL System Role or Ansible — so post-quantum enforcement is consistent across the fleet.
* *Look beyond SSH.* System-wide crypto policies affect many applications, not just OpenSSH. Review how the same policy influences TLS, your web servers, and other services, and plan which workloads need post-quantum protection first based on the confidentiality lifetime of their data.
* *Build a migration plan.* Identify the long-lived, high-value data in your environment — the records most exposed to HNDL — and prioritize moving those connections to post-quantum algorithms.
* *Explore RHEL 10 security hardening.* Continue with the broader RHEL 10 security hardening documentation to combine post-quantum cryptography with the rest of your defense-in-depth strategy.
